## 15.1 Address Translation

### Logical vs Physical Address

```text
Logical Address (CPU) → MMU → Physical Address (Memory)
```

- **Logical (Virtual) Address**: Generated by CPU during execution; seen by programmer and user process.
- **Physical Address**: Loaded into memory address register (MAR) of physical RAM.
- **MMU (Memory Management Unit)**: Hardware device mapping virtual to physical addresses at runtime.

### Hardware Support

- **Base / Limit Registers**: Provide basic hardware relocation and memory protection.
  - **Base Register**: Holds the smallest physical memory address allocated to the process.
  - **Limit Register**: Specifies the range (size) of the logical address space.
  - **Legal Range Condition**:
    ```text
    0 ≤ Logical Address < Limit
    ```
  - **Address Computation**:
    ```text
    Physical Address = Base + Logical Address
    ```
  - **Trap Mechanism**: If `Logical Address ≥ Limit`, the CPU hardware triggers an addressing trap (**Segmentation Fault / Illegal Memory Access**) to the OS kernel.
- **Memory Management Unit (MMU)**: Performs run-time address translation transparently to software.
- **Page Table Base Register (PTBR)**: Processor control register pointing to the base of the current process's active page table.

## 15.2 OS Support

### Memory Allocation Strategies

When allocating contiguous variable-sized memory blocks from a pool of free holes:

| Strategy | Description | Characteristics & Trade-offs |
|----------|-------------|------------------------------|
| **First Fit** | Allocate the first hole that is large enough | Fastest search; stops at the earliest available candidate. |
| **Best Fit** | Allocate the smallest hole that is large enough | Requires scanning the entire list (unless ordered); leaves small unusable leftover holes. |
| **Worst Fit** | Allocate the largest available hole | Leaves the largest remaining hole (more usable for subsequent allocations); slowest in practice. |

### Memory Protection

- **Valid / Invalid Bits**: Hardware flags in translation tables indicating whether an address falls within the process's allocated address space.
- **Protection Bits**: Specify access permissions (`Read`, `Write`, `Execute`) per page or segment.
- **System Traps**: Any unauthorized write to a read-only page triggers a hardware protection violation.

### Shared Pages

- **Read-Only Code Sharing**: Pure code (reentrant routines, shared C libraries) mapped with identical physical addresses across multiple process address spaces.
- **Copy-On-Write (COW)**: Pages shared read-only upon process creation (`fork()`); physical copy allocated only when either process writes to the page.

## 15.3 Dynamic Loading & Linking

### Dynamic Loading

- Routines are kept on secondary storage in relocatable load format.
- A routine is **loaded into memory only when called** by the running program.
- Unused routines (e.g., error handling code, diagnostic routines) are never loaded into physical RAM.
- **Benefit**: Significantly reduces working memory footprint and accelerates application boot time.

### Dynamic Linking

- Resolving external symbols and linking is **postponed until program execution time**.
- A small stub replaces library routine calls to locate and load the shared object if not already resident.
- **Single Shared Copy**: Only one copy of the library code resides in physical RAM across all processes.
- **Shared Library Extensions**: `.so` (Linux Shared Objects), `.dll` (Windows Dynamic Link Libraries), `.dylib` (macOS).

## 15.4 Memory-Mapped Files (`mmap()`)

The `mmap()` system call maps a file or anonymous memory region directly into the process's virtual address space, converting disk I/O operations into standard pointer memory reads and writes.

```c
#include <sys/mman.h>

void *mmap(void *addr, size_t len, int prot, int flags, int fd, off_t offset);
// Maps file descriptor fd into memory — treats file I/O as memory access

int munmap(void *addr, size_t len);  // Unmaps the designated memory region
```

### Parameters & Configuration Flags

| Parameter | Type / Macro | Description |
|-----------|--------------|-------------|
| `addr` | `void *` | Starting address hint (`NULL` requests the kernel to select a page-aligned address) |
| `len` | `size_t` | Length in bytes of the memory mapping |
| `prot` | Bitwise OR | Page access protections: `PROT_READ`, `PROT_WRITE`, `PROT_EXEC`, `PROT_NONE` |
| `flags` | Bitwise OR | `MAP_SHARED` (updates flush to disk & visible to other processes) vs. `MAP_PRIVATE` (COW mapping; changes remain private) |
| `fd` | `int` | Open file descriptor from `open()` syscall |
| `offset` | `off_t` | Offset within the file to begin mapping (must be an integer multiple of page size) |

### Common Systems Use Cases

1. **High-Throughput File I/O**: Eliminates repetitive `read()` / `write()` syscall overhead and redundant buffer copying.
2. **Shared Memory IPC**: Combining `MAP_SHARED` with `MAP_ANONYMOUS` creates shared memory regions between parent and child processes.
3. **Executable & Shared Library Loading**: Operating system dynamic linkers (`ld.so`) use `mmap` to load text and data segments.
4. **Out-of-Core Processing**: Managing database indexes and video files larger than physical RAM via automatic demand paging.

## 15.5 Key Takeaways

1. **Base & Limit Registers**: Provide fundamental hardware protection and dynamic relocation.
2. **MMU Function**: Seamlessly translates CPU-issued logical addresses to MAR physical memory locations.
3. **Contiguous Allocation**: First Fit offers optimal speed; Best Fit minimizes leftover hole size but worsens external fragmentation.
4. **Dynamic Loading vs. Linking**: Loading defers routine allocation until called; linking defers external symbol resolution and enables RAM sharing.
5. **Memory Mapping (`mmap`)**: Bridges memory management and disk storage by treating file blocks as virtual memory addresses.

## 15.6 Exam-Relevant MCQ Patterns

??? question "MCQ Pattern 1: Base and Limit Register Traps"
    A CPU generates a logical address of `0x0350`. The base register contains `0x4000` and the limit register contains `0x0300`. Which action occurs?
    
    - [ ] A) The physical address `0x4350` is accessed.
    - [x] B) A trap (segmentation/addressing error) is generated by the hardware.
    - [ ] C) The address wraps around to `0x4050`.
    - [ ] D) The limit register is dynamically expanded.

    ??? success "Explanation"
        The legal address condition is `0 <= Logical Address < Limit`. Here, `0x0350 >= 0x0300`, which violates the limit boundary. The MMU hardware intercepts this and generates a trap.

??? question "MCQ Pattern 2: MAP_SHARED vs. MAP_PRIVATE Semantics"
    When process $P_1$ writes to a memory region mapped with `mmap()` using `MAP_PRIVATE`, which statement is true?
    
    - [ ] A) The underlying disk file is immediately updated.
    - [ ] B) Other processes mapping the same file see the change.
    - [x] C) A private copy-on-write page is created for $P_1$, leaving the original file unchanged.
    - [ ] D) The kernel terminates $P_1$ with `SIGSEGV`.

    ??? success "Explanation"
        `MAP_PRIVATE` configures copy-on-write (COW) semantics. Any modifications are isolated to the calling process and are not committed to the underlying file.

## 15.7 Practice Problems

### Problem 1: Base/Limit Address Validation
Given:
- Base Register = `21000`
- Limit Register = `4500`

Evaluate whether the following logical addresses are legal and determine their resulting physical addresses:
1. Logical Address `250`
2. Logical Address `4500`
3. Logical Address `3800`

??? success "Solution Trace"
    1. `250 < 4500` &rarr; **Legal**. Physical Address = `21000 + 250 = 21250`.
    2. `4500 >= 4500` &rarr; **Illegal**. Triggers hardware trap (limit violation).
    3. `3800 < 4500` &rarr; **Legal**. Physical Address = `21000 + 3800 = 24800`.

### Problem 2: Dynamic Allocation Strategy Trace
Given free holes in memory of sizes: `100 KB`, `500 KB`, `200 KB`, `300 KB`, and `600 KB` (in order).
Trace which hole is selected for an incoming request of `212 KB` under:
1. First Fit
2. Best Fit
3. Worst Fit

??? success "Solution Trace"
    - **First Fit**: Scans in order &rarr; `100 KB` (too small) &rarr; **`500 KB` hole chosen** (leaves `288 KB` hole).
    - **Best Fit**: Scans all holes &rarr; candidate holes `≥ 212 KB` are `500 KB`, `300 KB`, `600 KB`. Smallest candidate is **`300 KB` hole chosen** (leaves `88 KB` hole).
    - **Worst Fit**: Scans all holes &rarr; largest hole is **`600 KB` hole chosen** (leaves `388 KB` hole).
